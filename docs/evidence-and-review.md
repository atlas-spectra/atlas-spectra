# Evidence, provenance, and review

Atlas Spectra treats epistemic status as data. A value or relationship is incomplete if a consumer cannot tell where it came from, whether it was measured or derived, what conditions apply, and whether a human has reviewed it.

## Evidence basis

`evidence.basis` answers **what kind of support is this?**

- `direct_measurement` — the value or signal is directly measured by an instrument or observation procedure.
- `established_reference` — an accepted standard, reference table, or authoritative published value.
- `model_derived` — inferred from a scientific model rather than directly measured in this record.
- `computed_derivation` — produced by an explicit deterministic computation or transformation from other values.
- `statistical_correlation` — supported by statistical association without implying a physical mechanism.
- `hypothesis` — proposed but not established.
- `subjective_report` — a reported percept, experience, or judgment.
- `traditional_association` — a cultural or traditional association that is not promoted to scientific mechanism.
- `disputed` — materially contested evidence or interpretation.
- `refuted` — evidence supports rejection of the claim or relationship.

Evidence basis is separate from relationship category. For example, a `CORRELATED_WITH` edge is statistical even if the correlation itself is directly measured, while `SAME_NUMERICAL_FREQUENCY_AS` remains numerical regardless of how accurately both values are known.

## Review lifecycle

`evidence.review_status` answers **what has happened to this evidence inside Atlas Spectra?**

- `imported` — ingested from a source but not yet independently reviewed.
- `machine_derived` — generated by an automated derivation or discovery process.
- `unreviewed` — authored or imported but awaiting human review.
- `reviewed` — a human has checked the representation against its cited evidence.
- `verified` — a stronger review state for claims whose source, value, conditions, and derivation have been explicitly verified.
- `disputed` — review identified a substantive unresolved disagreement.
- `superseded` — retained for history but replaced by newer evidence or interpretation.
- `rejected` — reviewed and not accepted into the trusted graph.

`verified_on` records the date of the most recent verification when that distinction matters.

## Field-level provenance

Manifest-level bibliographies are not enough. Important quantitative values use `provenance` entries whose `target` is a JSON Pointer to the field or object being supported.

A provenance target may cover a whole object:

```json
{
  "target": "/frequency_profile/rate",
  "evidence": {
    "basis": "established_reference",
    "review_status": "reviewed",
    "source_refs": [{"id": "source.example"}],
    "locator": "Table 2"
  }
}
```

An ancestor target such as `/frequency_profile` also covers quantitative descendants of that object. CI requires **traceable** provenance coverage for the primary quantitative content of every known frequency-profile representation. A pointer alone is not provenance: a field-level provenance entry must contain at least one `source_ref` or a non-empty `derivation` trail before CI counts it as coverage.

Extraction metadata does not substitute for origin. `extraction` describes how a value was captured from a source and therefore should accompany `source_refs`; an extraction object without a source reference does not make a provenance entry traceable. Relationships and claims carry their evidence inline instead and are not subject to this field-provenance coverage rule.

## Sources and extraction metadata

A `source` identifies the publication, standard, dataset, documentation, or other origin. Evidence can then narrow the citation with:

- `source_refs` — source IDs declared in the manifest.
- `locator` — page, table, section, figure, row, record identifier, or other precise location.
- `extraction` — structured metadata about how the source value was captured.
- `derivation` — the computation or reasoning that produced a derived value.

`extraction` may contain the source's `raw_value`, `raw_unit`, a short `excerpt`, an extraction `method`, and notes. The raw representation is useful when the canonical Atlas value has been normalized or otherwise transformed.

Do not duplicate large source passages in `excerpt`; it exists for compact value/context capture, not document reproduction.

## Uncertainty and confidence

`uncertainty` and `confidence` are different concepts.

- evidence-level `absolute` and `asymmetric` uncertainty are self-describing and **must include a unit**; they may also include a unit URI.
- evidence-level `relative` uncertainty is dimensionless and therefore does not require a unit.
- quantity-level `uncertainty` travels with the normalized quantitative value itself and inherits the quantity's unit.
- `confidence` is an epistemic score from 0 to 1 and must not be used as a substitute for measurement uncertainty or statistical significance.

Evidence objects are also used by relationships and non-quantity claims, so an evidence-level absolute uncertainty must never rely on a provenance target to infer its unit. When both evidence-level and quantity-level uncertainty are present, they should agree or the derivation should explain the difference.

## Conditions and mechanism status

`condition_refs` identify the local conditions under which evidence applies. `mechanism_status` records whether a physical mechanism is `known`, `proposed`, absent (`none`), not applicable, or unknown.

This is especially important for cross-domain discovery. A numerical match with `mechanism_status: none` must never be rendered as equivalent to a known physical coupling.

## Frontend presentation contract

For any important quantitative value, the UI should be able to expose:

1. the value and uncertainty, if present;
2. whether it is measured, referenced, modeled, computed, correlated, hypothetical, subjective, disputed, or refuted;
3. the source and precise locator, or the explicit derivation trail for a derived value;
4. raw/extracted source metadata when available;
5. the applicable conditions;
6. derivation details for computed or modeled values;
7. review status and verification date.

For relationships, additionally show the relationship category and mechanism status. Physical, mathematical, statistical, numerical, subjective, and epistemic edges must remain visually distinguishable. In particular, `SAME_NUMERICAL_FREQUENCY_AS` should be presented as a coincidence unless separate evidence establishes a stronger relationship.

## Example: source value plus uncertainty

The carbon-dioxide bending-mode seed stores the normalized spectral position in the frequency profile and records its NIST source representation in evidence metadata:

```json
{
  "target": "/frequency_profile/lines/0/position",
  "evidence": {
    "basis": "established_reference",
    "review_status": "reviewed",
    "source_refs": [{"id": "source.nist-webbook.co2-vibrations"}],
    "locator": "πu, mode 2, Bend",
    "extraction": {
      "method": "manual",
      "raw_value": 667.38,
      "raw_unit": "cm^-1"
    },
    "uncertainty": {
      "type": "absolute",
      "value": 1,
      "unit": "cm^-1"
    },
    "mechanism_status": "known"
  }
}
```

This keeps source fidelity, normalized data, and epistemic metadata independently inspectable.
